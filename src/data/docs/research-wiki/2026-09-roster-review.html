현재 설계를 살리면서,
비교와 근거를 보강하기

Full turn 0, cold KV 보관, 질문별 재선택, hot/cold 압축 구조를 유지한 채 살펴볼 논문과 실험을 정리했습니다. 목표는 기존 방법을 충분히 비교한 뒤에도 남는 ROSTER의 기여를 확인하는 것입니다.

우선순위   공개 코드가 있는 MixKV·ReKV부터 적용 범위를 살펴보고, 현재 구현에서 비교군과 ablation을 보강합니다. SparseVILA는 개념·차별성 확인용으로 두고 구현을 먼저 요구하지 않습니다.

01

추가로 살펴볼 논문

먼저 1·2번의 공개 구현을 살펴봅니다. 3·4번은 현재 방법과 겹치는 범위를 읽고, 구현 부담을 확인한 뒤 비교 범위를 정합니다.

1. MixKV ↗
공개 코드 · 우선 탐색

더 강한 선택 방식과 비교하기

왜 필요한가: 현재 재선택의 이득이 단순한 attention ranking을 개선한 결과인지, ROSTER의 window·cold 관리에서 오는 추가 이득인지 구분할 수 있습니다.

읽을 부분과 적용 방법›

논문에서 볼 부분

Attention 중요도에 Value norm과 Key diversity를 결합해 남길 KV를 고르는 방식입니다.

현재 설계에 붙이는 방법

ROSTER의 full archive·압축 방식·재선택 주기는 유지하고, selector를 MixKV 방식으로 바꾼 비교군을 만듭니다. Token/window 단위가 다르면 그 차이도 명시합니다.

확인할 기여: 같은 보관·전송 조건에서도 현재 선택 방식의 이득이 남는지, 또는 MixKV를 넣으면 전체 구조의 품질이 더 좋아지는지 확인합니다.

공식 코드 ↗

공개 코드는 확인했지만 우리 모델에서 바로 동작한다고 검증한 것은 아닙니다. 앞선 정적 검사에서 일부 mixing weight·분기 구현의 주의점을 확인했으므로 논문과 실제 실행 경로를 대조합니다. 이 비교군은 원형 재현과 구분해 “MixKV selector를 적용한 ROSTER”로 보고합니다.

2. ReKV ↗
공개 코드 · 우선 탐색

보관한 visual KV를 다시 찾는 방법과 비교하기

왜 필요한가: Visual KV를 외부 메모리에 보관하고 질문에 맞게 가져오는 선행연구입니다. Offloading과 재접근에 더해 우리 방법이 무엇을 개선하는지 설명하는 데 중요합니다.

읽을 부분과 적용 방법›

논문에서 볼 부분

질문과 관련된 visual KV block을 찾는 방식, CPU archive와 GPU cache의 관리, 전송 비용을 줄이는 구현을 봅니다.

현재 설계에 붙이는 방법

ReKV는 streaming video 대상이므로 전체 시스템의 이식을 전제로 하지 않습니다. 검색·cache 관리에서 같은 이미지의 반복 질문에 적용 가능한 부분을 골라, 동일 archive·정밀도·자원 상한에서 비교합니다.

확인할 기여: ROSTER의 spatial window, 압축, 질문별 재선택이 기존 retrieval 방식보다 품질·메모리·전송 비용 중 어떤 축을 개선하는지 확인합니다.

공식 코드 ↗

원형 성능과 우리 환경에 맞춘 adaptation은 다른 행으로 보고합니다. Immutable CPU master를 유지하고 GPU 사본만 버리는 clean eviction은 ReKV에도 있으므로 자체 신규 기여로 세지 않습니다.

3. VL-Cache ↗
읽고 구현 범위 판단

VLM에 맞춘 KV 예산 배분 살펴보기

왜 필요한가: Activation pruning 외에도 직접적인 VLM KV 압축 연구가 있습니다. Layer별 예산과 visual/text 구분을 고려해야 비교군 범위를 충분히 잡을 수 있습니다.

읽을 부분과 적용 방법›

논문에서 볼 부분

Layer별 sparsity에 따른 cache budget 배분과 modality-aware token scoring을 봅니다.

현재 설계에 붙이는 방법

먼저 현재 예산 배분과 무엇이 다른지 표로 정리합니다. 전체 재현에 앞서, 총 KV 예산을 유지하면서 층별 배분만 바꾸는 제한된 비교가 가능한지 판단합니다.

확인할 기여: 동일 자원을 더 잘 배분하는 것만으로 현재 격차가 설명되는지, cold 보존과 재선택의 효과가 별도로 남는지 확인합니다.

이번 확인 범위에서 공식 구현 위치를 확보하지 못했습니다. 바로 실행할 baseline으로 약속하지 않고 논문 분석을 먼저 합니다. 전체 방법을 재현하지 않았다면 VL-Cache-inspired 비교라고 명시합니다.

4. SpeCache ↗
Novelty 점검 · 조건부 비교

저정밀 보관과 고정밀 복구의 경계 확인하기

왜 필요한가: 저정밀 GPU 사본과 CPU의 원본 KV를 함께 두고 필요한 정보를 가져오는 연구입니다. Hot/cold 정밀도 관리의 기존 기여와 우리 차이를 구분해야 합니다.

읽을 부분과 적용 방법›

논문에서 볼 부분

Low-bit copy로 중요도를 판단하고 CPU에서 고정밀 KV를 가져오는 방식, 다음 decoding step의 prefetch를 봅니다.

현재 설계에 붙이는 방법

우선 cold에서 hot으로 옮긴 KV의 정밀도가 실제로 복구되는지 명세합니다. 2-bit 근사를 단순히 4-bit 형식으로 바꾸는 것만으로는 잃은 정보가 돌아오지 않습니다. 보완 실험 3에서 precision 손실이 확인될 때 복구 비교를 진행합니다.

확인할 기여: 같은 master 정밀도·codec을 허용해도 우리 정밀도 배분이나 전송 정책에 이점이 있는지 확인합니다. Precision 손실이 작다면 현재 압축 구조를 유지할 근거가 됩니다.

ICML 논문 페이지 ↗

Text LLM 대상 연구이며 이번 확인 범위에서는 공식 코드를 확보하지 못했습니다. 즉시 전체 재현을 필수 과제로 두지 않습니다. Per-token 원형과 query 단위 adaptation의 차이를 명시합니다.

필요할 때 참고할 논문: LightKV · SparseVILA · Palu›
LightKV ↗공정한 비교 설계

실제 심사에서 FastV의 기본 설정만 쓰는 비교가 지적됐습니다. 같은 압축률에서 baseline도 튜닝해야 한다는 근거로 활용합니다. Hidden-state aggregation을 수행하므로 현재 full-activation 구조에 그대로 넣는 것을 우선하지 않습니다. 해당 저자 답변 ↗

SparseVILA ↗개념·novelty 참고, 구현 우선순위 제외

Prefill과 decoding의 visual sparsity를 분리하고 질문에 맞게 KV를 고른다는 개념을 비교합니다. 전체 공식 재현 pipeline을 확인하지 못했고 설명으로부터 구현을 복원하는 부담도 커, 이번 보완 실험의 필수 baseline으로 두지 않습니다. 구현 여부와 별개로 관련연구에서의 차이는 설명합니다.

보충자료의 반복 QA는 이전 Q&A를 reset합니다. 우리 누적 대화 평가와 비교할 때 이 조건을 구분하면 충분하며, 이를 위해 전체 방법을 구현할 필요는 없습니다.

Palu ↗복원 비용이 병목일 때

Low-rank Value를 매번 전체 크기로 복원하지 않고 연산하는 방향을 참고합니다. 먼저 비용을 측정하고, Value 복원이 큰 비중을 차지할 때 구현 최적화 자료로 봅니다. 지금 새 kernel을 만드는 것을 선행 과제로 두지 않습니다.

02

현재 구현에서 보완할 실험

먼저 1·2번으로 비교 범위와 재선택의 효용을 보강합니다. 3·4번은 효과를 분리하고, 5번은 현재 비용의 개선 여지를 확인합니다.

01

Pruning 외의 KV baseline을 추가하기

이유: FastV·HiPrune 대비 결과에 더해, 같은 cold 보관 조건에서도 ROSTER의 장점이 남는지 보여 주면 novelty 근거가 강해집니다.

최소 비교군과 공정성 조건›
  • Full reference, 선택 없이 균일 4-bit로 보관하는 기준선, 현재 ROSTER, 재선택을 끈 ROSTER를 먼저 둡니다.
  • MixKV selector + 동일 ROSTER archive·압축 구조를 추가합니다. 다음으로 ReKV에서 적용 가능한 검색 방식을 비교합니다.
  • 방법의 원형과 우리 구조에 붙인 adaptation을 구분합니다. 같은 모델·입력·질문·validation tuning 예산을 사용합니다.
  • 동일 GPU·host 자원 상한에서 품질과 latency를 함께 비교합니다. 실제 전송량까지 강제로 같게 하면 적게 보내는 정책의 이득을 지우므로 주의합니다.

남길 결과·판단: 품질·GPU peak·host bytes·latency를 나란히 둔 표. 우위가 없더라도 어떤 모듈을 개선해야 하는지 판단하는 근거가 됩니다.

LightKV 답변의 NeXT-7B 정규화 평균 격차는 동일 55% KV compression에서 FastV 튜닝 후 8.48→0.98로 줄었습니다. 우리도 선택 layer를 튜닝한 방법과 default baseline만 비교하지 않습니다. 원문 표 ↗

02

질문이 다른 영역으로 옮겨 갔다가 돌아올 때 확인하기

이유: Cold evidence를 남기는 설계의 가치는 미래 질문에서 드러납니다. 평균 정확도에 더해, 어떤 질문 이동에서 재선택이 도움이 되는지 보여 주는 실험입니다.

질문 구성과 측정 항목›
  • 기존 같은-image 질문 묶음에서 관련 영역이 유지되는 경우, 다른 영역으로 이동하는 경우, A→B→A로 복귀하는 경우를 구분합니다. 영역 근거가 불명확하면 추정과 수동 확인 여부를 표시합니다.
  • 재선택 on/off와 실험 1의 강한 selector를 같은 조건에서 비교합니다. 정확도와 함께 cold에서 실제로 가져온 block·bytes를 기록합니다.
  • 독립 QA reset과 이전 Q&A를 누적하는 대화를 별도로 평가합니다. 독립 질문의 재배열을 실제 참조형 대화로 간주하지 않습니다.
  • 뒤쪽 turn에 긴 대화만 남는 영향을 피하도록 같은 dialogue 집합에서도 결과를 봅니다. 정답 영역 정보는 평가에만 쓰고 selector에 주지 않습니다.

남길 결과·판단: 질문 이동 유형별 품질과 전송 비용. Cold 복귀가 필요한 상황에서 효과가 집중되면 현재 설계의 필요성을 더 구체적으로 설명할 수 있습니다.

04

Window 구성과 선택 layer의 기여를 따로 보기

이유: 구조를 유지하면서도, 성능이 좋아지는 이유가 공간적 묶음인지 선택 시점인지 확인할 수 있습니다. 현재 방법 고유의 설계를 설명하는 직접적인 근거가 됩니다.

작게 시작할 ablation›
  • 같은 선택 layer와 정밀도에서 spatial window 방식과 token 단위 attention ranking을 비교합니다. 동일 token 수뿐 아니라 metadata를 포함한 실제 bytes도 보고합니다.
  • Window·압축 방식을 고정하고 선택 layer를 바꿉니다. Layer가 깊어질 때 추가되는 scout 비용과 품질을 함께 기록합니다.
  • 고정 selector와 질문별 reselection 비교를 연결해, 각 구성요소의 개별 효과와 필요한 조합을 확인합니다.
  • Layer·window size는 validation에서 선택하고 test 결과에 맞춰 조절하지 않습니다. 전체 조합을 한 번에 탐색하기보다 요인 하나씩 바꿉니다.

남길 결과·판단: 같은 자원 조건의 작은 ablation 표. 우리 구조에서 실제로 중요한 요소를 중심으로 기여 주장을 좁힐 수 있습니다.

05

현재 추가 비용이 어디서 발생하는지 분해하기

이유: 메모리·품질의 장점을 살리면서 개선할 구현 지점을 찾을 수 있습니다. 현재 기법을 바꾸기 전에 복원·전송·선택 중 큰 비용부터 확인합니다.

측정 항목과 후속 판단›
  • Turn 0과 후속 질문을 나눠 selection, H2D/D2H, dequant/Value 복원, dense lower-layer 연산을 측정합니다. 중첩된 전송·연산 시간을 이중으로 더하지 않습니다.
  • GPU 상주량, GPU peak/workspace, host archive·metadata를 분리합니다. Table 4의 visual KV 비율을 전체 추론 메모리 비율로 해석하지 않습니다.
  • 불변 CPU master가 이미 있으면 GPU 사본 eviction 때 불필요한 D2H가 없는지 확인합니다. Value 복원이 크면 Palu의 연산 방식을 참고합니다.
  • 답변 길이별로 고정 준비 비용이 얼마나 상각되는지 봅니다. 결과에 따라 memory–quality 장점과 latency 비용을 함께 제시합니다.

남길 결과·판단: 현재 ROSTER의 비용 분해와 동일 품질 조건의 개선 전후 비교. Latency가 줄지 않으면 절감한 메모리의 대가를 정확히 보고하는 것 자체가 유용한 결과입니다.
